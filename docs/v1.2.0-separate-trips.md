## 1. Scope

v1.1.0 handles one continuous trip that visits up to 5 cities. v1.2.0 adds **separate trips**: up to
5 trips, each with its own dates, its own destinations and its own first and last day at 75%, with
one combined total. Example: Mon to Tue in New York City, then Thu to Fri in Chicago.

Why: the live page promises "multiple trips". Entering two separate trips as one continuous trip
overstates the allowance (it bills lodging for nights at home and applies the 75% days only once).

**Decisions (19 Oct 2026):**
1. Up to **5 trips**. Each trip may have up to 5 destinations (full v1.1 flexibility per trip).
2. **Overlapping dates between trips are an error.** Trips that touch on the same day (trip 1
   returns 16 Oct, trip 2 departs 16 Oct) are also an error, with a hint to use Add another
   destination instead.
3. Trips may be entered in any order; results and the CSV are shown in the order entered.

**Not in v1.2.0:** meal deductions (v1.3.0), saving plans, Alaska / Hawaii / international.

## 2. Plan model

```
plan = {
  trips: [ trip, trip, ... ]   // 1 to 5, in the order entered
}
trip = { depart, return, over12, destinations[1..5] }   // exactly the v1.1 trip model
```

- **Trip 1** uses the existing fields (dates, switch, destination 1, destination rows, Add another
  destination). Nothing about it changes when it is the only trip.
- **Trip k (k ≥ 2)** is a cloned block with the same parts: Departure date, Return date, the
  same-day switch, Destination 1 (State, City or county), its own destination rows and its own
  Add another destination button.

## 3. Calculation rules

Rules 1 to 8 of the phase-4 spec and rules 1 to 8 of v1.1 §5 apply **per trip**, unchanged.
Additions:

1. **Each trip is calculated on its own** with `calculateTrip`. Its first and last day pay 75%.
   Nothing carries across trips.
2. **Plan totals** = the sum of the trips' days, lodging, M&IE, meals, incidentals and total.
   Exact values, summed; never round intermediate steps.
3. **Overlap check** (after every trip validates on its own): for every pair of trips, if
   `depart_a ≤ return_b` and `depart_b ≤ return_a` the plan is invalid. The later trip in entry
   order is the one marked. Message: "Trip {k} overlaps trip {j}. Check the dates." When the two
   touch on exactly one day, the message names the direction (k = the marked trip):
   - `depart_k = return_j`: "Trip {k} starts the day trip {j} ends. For one continuous trip, use
     Add another destination instead."
   - `return_k = depart_j` (the marked trip is earlier in time, entered later): "Trip {k} ends the
     day trip {j} starts. For one continuous trip, use Add another destination instead."
   - If both hold (two same-day trips on the same date), use the first.
   (`field`: `depart` of the marked trip in every case.)
4. **Same-day trips** (v1.1 rules 6 to 8) work per trip, each with its own switch. A plan may mix
   overnight and same-day trips. A same-day trip with its switch off contributes $0 but keeps the
   plan valid.
5. **365-day limit** stays per trip. There is no limit on the span of a plan.

**Validation order:** trip 1 in full (v1.1 order) → trip 2 in full → … → overlap check across all
trips. First failing check wins. Every error carries `trip` (0-based index), plus `dest` and `field`
as in §17.

**Code shape (suggested, not locked):** `calculatePlan({ trips: [tripInput, …] })` returns
`{ ok, trips: [tripResult, …], days, lodging, mie, meals, incidentals, total, rows[] }` where each
row adds `trip` (index). Keep `calculateTrip` and `calculate` unchanged so tests 1 to 34 run as they
are. Expose `calculatePlan` on `window.ItilitePerDiem`.

## 4. Form behaviour

**Default state (one trip):** identical to v1.1.0.

**Adding trips**
- An **"Add another trip"** button sits under trip 1's Add another destination button (below all
  destination rows), above the message line.
- Each click inserts a trip block: legend "Trip k", **Remove**, a dates line (see §17 style), Departure
  date, Return date, the same-day switch (hidden until the dates are equal), Destination 1 State and
  City or county, an empty destination list, and its own Add another destination button.
- The new trip's dates are empty. Its Destination 1 State is **prefilled with the previous trip's
  last destination state** (same reasoning as v1.1: easy to change).
- With 2 or more trips, a **"Trip 1"** title and dates line appear above trip 1's Departure date.
- At 5 trips the button is disabled and the note "Up to 5 trips." shows.
- **Remove** deletes the block; later blocks renumber (legend, labels, ids). Trip 1 can't be removed.
- Each trip's destination rows, Arrive on `min`/`max`, same-day switch and messages behave exactly as
  in v1.1, scoped to that trip. Destination ids become `pd-t{k}-dest-{m}-…` for trips 2+; trip 1
  keeps its v1.1 ids.
- Date fields of trips 2+ get `min`/`max` from `meta.json` like trip 1. No automatic min/max from
  other trips (validation handles overlap; typed dates bypass min/max anyway).

**Dates line per trip** (2+ trips): "12–16 Oct 2026 · 5 days · 2 cities" (or "· 1 city"); same-day:
"12 Oct 2026 · day trip". Shown from the dates alone, as in §17.

**Messages** (exact text)

| Situation | Message |
|---|---|
| Trip k has no departure date | Choose the departure date for trip {k}. |
| Trip k has no return date | Choose the return date for trip {k}. |
| Trip k return before departure | Trip {k}'s return date is before its departure date. |
| Trip k destination problems | v1.1 messages, prefixed when 2+ trips: "Trip {k}: Choose a city or county for destination 2." |
| Overlap | Trip {k} overlaps trip {j}. Check the dates. |
| Touching (trip k starts when trip j ends) | Trip {k} starts the day trip {j} ends. For one continuous trip, use Add another destination instead. |
| Touching (trip k ends when trip j starts) | Trip {k} ends the day trip {j} starts. For one continuous trip, use Add another destination instead. |

Trip 1 keeps its unprefixed v1.1 messages while it is the only trip.

Errors show on the trip's dates line in red (`is-error`) and mark the field (`aria-invalid`), and the
bottom message repeats them (one live region), as in §17.

**Summary line** (after a valid result)

| Plan | Example |
|---|---|
| One trip | unchanged (v1.1 examples) |
| Two trips | 2 trips, 5 days: San Francisco (1–3 Oct 2026) and North Dakota (standard rate) (10–11 Oct 2026). Total allowance $1,003. |
| Three or more | 3 trips, 6 days, 10–18 Oct 2026. Total allowance $645. (three North Dakota standard-rate trips of 2 days each) |

A multi-city trip is named by its first destination plus "and {n} more" in the two-trip form.

**Result panel**
- The five boxes show plan totals. With 2+ trips the "Trip total" label reads **"All trips total"**
  (hook `total-label`, optional).
- **By trip** list (2+ trips): one line per trip in entry order, with its name, dates line and total,
  cloned from `<template data-pd="trip-breakdown-template">`. A multi-city trip's destination lines
  follow it, indented (`is-sub`), using the existing `breakdown-template`. The title reads "By trip"
  (hook `breakdown-title`, optional; "By destination" stays for one multi-city trip).
- Lines add up to the plan total.

## 6. Export (CSV)

- Filename: one trip unchanged; several: `per-diem-trips-{first depart}-to-{last return}.csv`
  (earliest departure and latest return across trips).
- Header lines: `ITILITE per diem estimate`, then `Trips: {n}`, then one line per trip:
  `Trip 1: New York City, New York (12–16 Oct 2026)` (multi-city trips list their destinations as
  in v1.1), then `Source: …` and `Generated {date}`.
- Columns unchanged: `Date, Fiscal year, Location, Lodging (USD), Meals (USD), Incidentals (USD),
  Day total (USD)`.
- Rows grouped by trip in entry order. Before each trip's rows: a title row `Trip 1` (first cell only).
  Inside a trip: v1.1 destination subtotal rows where there are 2+ destinations. After each trip:
  `Subtotal: Trip 1` with its lodging, meals, incidentals and total. Then the existing **Total** row.
- Same-day trip with the switch off contributes one row with zeros and the note
  `Day trip of 12 hours or less: no per diem` in the Location cell.
- BOM, CRLF, quoting, formula guard, plain numbers: unchanged.
- Export is enabled only while the whole plan is valid.

## 8. Accessibility

- Each extra trip is a `<fieldset>` with a `<legend>` ("Trip 2"). Its destination fieldsets nest
  inside it, which is valid HTML.
- Focus moves only on the user's own action: after Add another trip, to the new trip's Departure
  date; after Remove, to the Add another trip button.
- One live region (the bottom message) as before. Trip status lines are linked to their Departure
  date with `aria-describedby`.
- Keyboard-only use must work end to end, including nested add and remove.
